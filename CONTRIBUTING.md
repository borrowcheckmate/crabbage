# Contributing

## Setup

Use the devcontainer, or install Rust via rustup; `rust-toolchain.toml` pins the version. Then:

```sh
git config user.email "ID+username@users.noreply.github.com"
cargo xtask hooks
```

Find your noreply address under GitHub → Settings → Emails. Only GitHub noreply addresses are accepted; the hooks and CI reject any other email.

Coverage and dependency checks need `cargo install --locked cargo-llvm-cov cargo-deny` (preinstalled in the devcontainer). `cargo xtask docker` needs Docker on the host; the devcontainer deliberately has no Docker access.

## Workflow

1. Every change starts from an issue. Split large work into sub-issues.
2. Branch from `main`, keep the change focused on one issue.
3. Write tests first or alongside. Every behaviour needs an automated test; nothing should depend on manual checks.
4. `cargo xtask pre-commit` runs on commit. `cargo xtask ci` runs the full suite locally.
5. Open a PR with a conventional title. PRs are squash-merged, so the title becomes the commit.

## Tasks

| Command | Purpose |
| --- | --- |
| `cargo xtask fmt [--check]` | Format |
| `cargo xtask lint` | Clippy, warnings denied |
| `cargo xtask test` | All tests |
| `cargo xtask docs` | Rustdoc, warnings denied |
| `cargo xtask coverage` | Line coverage ≥ 90% |
| `cargo xtask deny` | RustSec advisories, licenses, duplicate and wildcard deps, sources |
| `cargo xtask policy` | Repository rules, see ARCHITECTURE.md |
| `cargo xtask identity` | Anonymous git identity |
| `cargo xtask wasm` | Clippy on the WASM (hydrate) build, warnings denied |
| `cargo xtask docker` | Build the container image and smoke-test `/healthz` (needs Docker) |
| `cargo xtask ci` | Everything CI runs except coverage and docker |

## Commits

[Conventional commits](https://www.conventionalcommits.org): `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`, `style`, `revert`. release-plz derives versions and the changelog from them. No tool attribution, co-author trailers for tools, or "generated with" lines.

## Pull requests

Short and concrete: what changed, why, how it is tested. Link the issue with `Closes #N`. No filler.

## Issues

State the goal, point to the ARCHITECTURE.md section and modules involved, and list verifiable acceptance criteria. The reader should not have to read the whole codebase.

## Dependencies

Prefer the standard library. A new crate needs:

- the latest version, with `default-features = false` and only the features you use,
- an active, trustworthy maintainer and a license allowed in `deny.toml`,
- a passing `cargo xtask deny`,
- a sentence in the PR on why std is not enough.

Declare it in `[workspace.dependencies]` and inherit it in the crate.

## Tests and data

Tests must pass on any machine: no absolute paths, no network, no files outside the repository. Write temporary files under `std::env::temp_dir()`. Large fixtures are generated by code, never committed.

## Docker

Images build from pinned digests and pinned tool downloads, run as a non-root user from `scratch`, and are tested with a read-only filesystem, no capabilities, `no-new-privileges` and a port published on loopback only. Keep it that way.

## Releases

release-plz opens a release PR on every push to `main`, and tags a GitHub release when it is merged. PRs created with the default `GITHUB_TOKEN` do not trigger CI; configure a GitHub App token if you need checks on release PRs. To publish to crates.io, replace `git_only = true` with `publish = true` in `release-plz.toml` and add a `CARGO_REGISTRY_TOKEN` secret.
